Your Connection class is a small HTTP server component that sits between a raw TCP socket and your HTTP request handler.

TCP delivers bytes. HTTP gives meaning to those bytes. Your Connection class manages the process of turning those bytes 
into HTTP requests, executing those requests, and returning HTTP responses over the same TCP connection.

You are not simply writing a class that contains methods. You are implementing part of the machinery that a real HTTP server 
needs to handle incoming clients, incomplete requests, timeouts, persistent connections, and errors. 
Let's break it down from the architecture to the internal mechanics of every method.

A state machine is a system that has a defined set of states and changes from one state to another when particular events occur.

Your code uses these states:
State	Meaning
HEAD	Waiting for or parsing HTTP request headers
BODY	Reading the current request body
BUSY	Application handling is in progress
CLOSED	The connection is no longer accepting normal request processing


The intended lifecycle is approximately:
                     New connection
                             |
                             v
                           HEAD
                             |
                    Complete headers
                             |
                             v
                           BODY
                             |
                     Complete request
                             |
                             v
                           BUSY
                             |
                     Response completed
                             |
                   +---------+---------+
                   |                   |
                   v                   v
                 HEAD                CLOSED
             Keep-alive          Close requested

The transition from BUSY back to HEAD normally happens after the response has been completed, although that behavior depends on your respond module.
The connection can also transition to CLOSED because of a parsing error, timeout, peer disconnect, socket closure, or server shutdown.
Notice that HEAD does not mean the TCP connection has only received HTTP headers forever. It means the connection is currently in the phase of reading a new request's headers.
Once the server finishes responding to a request, the same connection can return to HEAD and receive another request.
That is how HTTP/1.1 persistent connections work.

What is a constructor?
A constructor is a special method that JavaScript executes when you create an instance using new.

For example:
const connection = new Connection(socket, server);

JavaScript creates a new object and invokes the constructor with two arguments:
socket
server

The constructor initializes the object's state and establishes its relationship with the TCP socket.
Think of it as the initialization phase of a connection.

Before this constructor runs, the new connection object does not yet have the properties your methods expect.

After initialization, it has the references, buffers, state variables, and event listeners required to manage the connection.

Why accept socket and server?
constructor(socket, server)
These arguments represent two different responsibilities.
socket represents the individual network connection.

It provides access to the underlying TCP communication channel.

Your class uses it to:
- Receive data.
- Write HTTP responses.
- Detect when the client finishes sending data.
- Detect socket errors.
- Close the connection.
server represents the broader server application.
Your class uses it to:
- Access server configuration.
- Execute the request handler.
- Participate in connection tracking and server shutdown.
This is an example of dependency injection: the connection receives the objects it needs rather than creating its own server or TCP socket.

That makes the class reusable across different requests and server configurations.

Example output:

- Multiple requests on the same TCP connection.

4.3 Store the socket
this.socket = socket;

This saves the socket reference on the instance.

Without this assignment, other methods would not be able to access the socket through this.socket.

For example:
this.socket.write("HTTP/1.1 200 OK\r\n\r\nHello");

this.socket.write("HTTP/1.1 200 OK\r\n\r\nHello");

Or:
this.socket.destroy();

You could pass the socket into every method individually, but that would be unnecessary because every method belongs to the same connection.
Storing it once establishes ownership of the socket reference for the lifetime of the object.

**************
4.4 Store the server
this.server = server;

This allows the connection to access shared server-level functionality.

Later, you use:
res = await this.server.handler(req);

The connection itself does not need to know whether the application is serving weather data, authentication requests, or user profiles.
It only needs to know how to invoke the server's handler.
This is a separation between transport-level processing and application-level behavior.

4.5 Store configuration
this.opts = server.opts;

Your connection needs configuration values such as:
this.opts.keepAliveTimeoutMs
this.opts.headerTimeoutMs
this.opts.bodyTimeoutMs
this.opts.maxHeaderBytes
this.opts.maxBodyBytes

These settings determine how long the server waits and how much request data it permits.
Your connection can now use these settings without hardcoding them into every method.

One design consideration: this.opts references the same object as server.opts; it does not create a copy. If the server mutates that object, the connection sees those changes.

4.6 Initialize the byte buffer
this.buff = Buffer.alloc(0);

This is one of the most important lines in the constructor.

A TCP socket gives your application byte sequences, represented in Node.js by Buffer objects.

Your parser cannot assume that each incoming chunk represents a complete request.

Consider this incoming request:
GET /health HTTP/1.1
Host: localhost

The client might send the terminating \r\n\r\n in a later chunk.

Your connection needs somewhere to store the bytes until it has enough data to parse the headers.

That storage is:
this.buff

Initially:
this.buff = Buffer.alloc(0);
The buffer has zero bytes.

When data arrives, onData() adds the new chunk to it.
The buffer therefore represents bytes received but not yet fully consumed by the connection's processing logic.
This is a key distinction: your buffer is not necessarily just the current request. It may also contain bytes belonging to subsequent requests.

4.7 Initialize the state
this.state = "HEAD";

A newly accepted connection begins by waiting for an HTTP request.

The first normal processing phase is therefore HEAD.

Your pump() method uses this state to determine which operation to perform.

For example:
if (this.state === "HEAD") {
    // Parse request headers.
}

Later:
this.state = "BODY";

And after the request is ready:
this.state = "BUSY";

The state variable prevents the connection from treating every incoming byte as if it belonged to the same processing phase.

4.8 Initialize the current request
this.req = null;

Initially, the connection has no parsed HTTP request.

Once the headers have been parsed, you assign the resulting request object:
this.req = parseHead.call(
    this,
    this.buff.subarray(0, end)
);

The req property then holds information about the request being processed.

Depending on your parser's implementation, this may include:
{
    method: "GET",
    target: "/health",
    version: "HTTP/1.1",
    headers: {
        host: "localhost"
    }
}

This is an illustrative shape; your actual parser determines the request object's structure.

Why use null initially?

Because it clearly represents the absence of a parsed request.
The distinction is useful:
this.req === null
means no current parsed request is stored, while:
this.req !== null
means the connection has a request object available.

4.10 Initialize timer state
this.timer = null;
this.headerTimerArmed = false;
this.bodyTimerArmed = false;

The timer reference stores the currently active timeout.

The two Boolean flags indicate whether the header or body timeout has been armed.

Why separate flags?

Because the connection uses one timer reference for several different waiting periods:
1. Waiting for the next request on an idle keep-alive connection.
2. Waiting for the request headers.
3. Waiting for the request body.
The timer reference answers:
Which timeout is currently scheduled?

The flags answer:
Have we already started the timeout for this processing phase?

For example:
if (!this.headerTimerArmed) {
    this.setTimer(this.opts.headerTimeoutMs);
    this.headerTimerArmed = true;
}

This prevents each incoming chunk from restarting the header timeout.

That distinction matters when a client sends a request extremely slowly.

4.11 Initialize the close-after-response flag
this.closeAfterResponse = false;

This flag indicates that the connection should close after the current response rather than continuing to accept another request.

You use it in:
onPeerFin()

and:
drain()

For example, a client might finish sending data while your server is still processing the request.
Rather than necessarily destroying the socket immediately, your connection can remember that it should close after responding.
The response implementation must actually honor this flag for the intended behavior to work.

4.12 Disable Nagle's algorithm
socket.setNoDelay(true);

TCP's Nagle algorithm can combine small outgoing writes to reduce the number of small packets.
Disabling it allows small writes to be sent without waiting for that algorithm to coalesce them.
This can reduce latency for request/response protocols that send small amounts of data.
However, it is not automatically faster in every situation. The effect depends on traffic patterns and network conditions.
Your code chooses lower latency for small writes over the potential packet-efficiency benefits of Nagle's algorithm.

4.13 Register socket event listeners
socket.on('data', (chunk) => this.onData(chunk));
socket.on('end', () => this.onPeerFin());
socket.on('error', () => socket.destroy());
socket.on("close", () => this.onClose());

This connects the socket's lifecycle to your connection object's lifecycle.
The data event
socket.on('data', (chunk) => this.onData(chunk));

Whenever Node.js emits incoming socket data, the callback passes the chunk to your connection.

For example:
Socket receives bytes
        |
        v
'data' event
        |
        v
onData(chunk)
        |
        v
Append bytes to buffer
        |
        v
pump()

The connection does not need a separate external function to be called every time data arrives.

It reacts to the socket event.
The end event
socket.on('end', () => this.onPeerFin());

This event indicates that the remote peer has finished sending data on its writable side of the TCP connection.

It does not necessarily mean that all previously written data has disappeared or that the socket's close event has already occurred.

Your onPeerFin() method decides what this means for the connection's HTTP lifecycle.
The error event
socket.on('error', () => socket.destroy());

This handles socket errors by destroying the socket.

Without an appropriate error listener, an emitted socket error can cause an unhandled error event and terminate the Node.js process.

Your listener prevents that particular failure mode by explicitly handling the event.

However, the current implementation discards the error details.

For debugging, you would usually want to log the error or classify it appropriately:
socket.on("error", (err) => {
    console.error(
        `Connection ${this.id} socket error:`,
        err.message
    );

    socket.destroy();
});

In production, avoid logging sensitive request data or other confidential information.
The close event
socket.on("close", () => this.onClose());

This lets your connection perform cleanup after the socket closes.

For example:
this.clearTimer();
this.server.connections.delete(this);

This is important because the server needs to stop tracking connections that no longer exist.

4.14 Start the keep-alive timeout
this.setTimer(this.opts.keepAliveTimeoutMs);

A connection may remain open after a response so that the client can reuse it.

But what if the client never sends another request?

Without a timeout, the server may retain idle sockets and their associated resources for too long.

The initial timer sets a limit on how long the connection can remain idle.

Your onTimeout() method determines what happens when the timer expires.
Constructor summary
The constructor does five fundamental jobs:
1. Assigns the socket and server dependencies.
2. Initializes all per-connection state.
3. Establishes the connection's event listeners.
4. Configures the socket's behavior.
5. Starts the initial timeout.
The constructor does not parse a request or execute application logic. It prepares the object to handle those operations when the corresponding events occur.

5. Timer management: setTimer() and clearTimer()
Your timer methods are small, but they control an important part of network resource management.
5.1 setTimer(ms)
setTimer(ms) {
    clearTimeout(this.timer);

    this.timer = setTimeout(
        () => this.onTimeout(),
        ms
    );
}

Let's examine the mechanism.

Suppose the connection is waiting for request headers and needs a 10-second timeout.

You call:
this.setTimer(10000);

The following happens:
1. Any previously scheduled timeout is cancelled.
2. A new timeout is scheduled.
3. After approximately 10 seconds, Node.js runs the callback if the timeout has not been cancelled.
4. The callback invokes this.onTimeout().
Conceptually:
setTimer(10000)
       |
       v
Cancel previous timer
       |
       v
Create a new timer
       |
       v
Wait for approximately 10 seconds
       |
       v
onTimeout()

Why cancel the previous timer first?

Because the connection has only one this.timer reference.

You do not want an older timeout to remain active after the connection has moved to a new processing phase.

For example:
HEAD timeout
     |
     v
Headers completed
     |
     v
Cancel HEAD timeout
     |
     v
Start BODY timeout

There is a subtlety here: JavaScript timers are not precise deadlines. Their callbacks can run later than scheduled, depending on event-loop activity.
Also, clearTimeout(null) is harmless, so the method works when no timer is currently active.

********
5.2 clearTimer()
clearTimer() {
    clearTimeout(this.timer);
    this.timer = null;
}

This cancels the currently scheduled timeout and resets the reference.

Why set the property to null after clearing it?

Because the object's state now accurately represents the fact that no timer is currently registered in this.timer.

For example, after successfully parsing the headers:
this.clearTimer();

The connection should no longer be subject to the header timeout.

Later, if it needs a body timeout, it can start another timer.
Important design detail
Your implementation uses one timer for multiple purposes rather than separate timer objects for headers, bodies, and keep-alive.

That is a reasonable design for a small connection state machine, provided that every state transition correctly clears, resets, and rearms the timer.

The Boolean flags are necessary because the timer reference alone does not tell you which phase initiated the current timeout.

6. onTimeout(): What happens when a client takes too long?
Your method:
onTimeout() {
    if (this.state === "HEAD" && this.buff.length === 0) {
        this.state = "CLOSED";
        this.socket.destroySoon();
    } else if (
        this.state === "HEAD" ||
        this.state === "BODY"
    ) {
        this.fail(408, "Request Timeout");
    }
}

This method distinguishes between two situations.
Situation A: The connection is idle
if (this.state === "HEAD" && this.buff.length === 0)

Both conditions must be true:
- The connection is in the header-reading state.
- Its buffer is empty.
That means the server is waiting for a new request and has not received any bytes for it.

Example:
Browser requests /health
Server responds 200 OK

Connection remains open
Buffer = empty
State = HEAD

Client sends nothing for too long
Keep-alive timeout expires

The server can close the idle connection without generating a 408 response.
this.state = "CLOSED";
this.socket.destroySoon();

The state is changed first, preventing subsequent processing from treating the connection as open.

destroySoon() is intended to end the socket and destroy it after pending writes have been flushed.

Since this branch is closing an idle connection, there should not normally be a pending HTTP response.
Situation B: A request is incomplete
else if (
    this.state === "HEAD" ||
    this.state === "BODY"
)

The connection is actively reading a request, but the client has not completed it before the timeout.

Examples:

Incomplete headers:
GET /api/weather HTTP/1.1
Host: localhost
X-Custom-Header:

The client has started sending a header but has not completed the header section.

Incomplete body:
POST /api/users HTTP/1.1
Host: localhost
Content-Length: 100

{"name":"Umair"

Suppose the request declares a 100-byte body but the client stops sending bytes before the body is complete.

Your connection eventually calls:
this.fail(408, "Request Timeout");

That method attempts to send an HTTP timeout response and close the connection.

Why not use one timeout for everything?
Because idle waiting and incomplete requests are different conditions.

An idle keep-alive connection is not necessarily doing anything wrong. It is waiting for the next request.

An incomplete request, however, is consuming resources while the server waits for the client to finish sending the message.

Different timeouts let you treat these situations differently.
A limitation to understand
Your onTimeout() method has no explicit action for the BUSY state.

For example, if:
this.state === "BUSY"

when the timer callback executes, neither branch runs.

Whether that can happen in practice depends on how your respond implementation manages timers.

You should not assume that this timer imposes an application-handler execution deadline. It does not currently do so.

If you want to prevent application handlers from running indefinitely, that requires a separate application timeout strategy, potentially involving cancellation or an AbortSignal.
